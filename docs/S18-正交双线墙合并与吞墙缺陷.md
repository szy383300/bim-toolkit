# S18 · 正交双线墙不合并 + 三处吞墙缺陷

日期：2026-10-07 ｜ 影响文件：`lib/bimconv_walls.py`、`tools/plan_eval.py`、`tools/probe_double_line.py`

## 起点：S17 的"下一步"排序是错的

S17 把"单位归一"列为第一优先级。量完真图才发现这个排序站不住：
**6/6 张真图 `$INSUNITS=0` 且坐标本来就是毫米数**，单位那条对用户的实际体验是 0 影响。
真正决定"效果不好"的是墙。

## 一、我先犯了一个错，然后被自己的测量纠正

我读 `_create_wall` 发现它对每条墙层图元逐段建墙，就下结论"没有双线聚类、
一面墙建两段"。**这是错的** —— `consolidate_walls` 在 `script.py:310` 确实被调用，
我只看了被调用函数没看调用链。

纠正方式是量，不是再读一遍代码：

| 图 | 原始墙段 | 聚类后 | 原始真重复 | 聚类后残余 |
|---|---|---|---|---|
| r1 | 2738 | 684 | 68.0% | 33.0% |
| r2 | 6317 | 1508 | 65.5% | 2.5% |
| r4 | 8034 | 1523 | 82.0% | 3.0% |
| r5 | 10538 | 1820 | 73.5% | 18.0% |
| r6 | 749 | 165 | 68.5% | 32.7% |

聚类在工作（段数降 79%），但**残余重复率 2.5~33%，且 5/5 张图里每一条残余重复
都是轴对齐（水平/垂直）墙，一个例外都没有**。

## 二、根因：正交开口双线墙落在三个处理器的缝隙里

`consolidate_walls` 的链路是：
`_outline_centerline_plans` → `_build_wall_plans` → `_resolve_wall_overlaps` → `_diag_dedupe` → `_rechain`

| 处理器 | 管什么 | 漏了什么 |
|---|---|---|
| `_outline_centerline_plans` | **闭合**双线轮廓 → 中线 | 开口双线 |
| `_resolve_wall_overlaps` | 轴对齐，但只去**同心**重复线（`_MERGE_TOL_MM=2`） | 相隔 240mm 的双线 |
| `_diag_dedupe` | 双线取中，但 `if _seg_axis_rect(q) is None` **只放行斜线** | 全部正交墙 |

v2.11e 的注释写着"轴对齐墙原样透传"——那是当时为了修斜坐标系图加的分支，
**正交墙被当成"已经有 `_resolve_wall_overlaps` 管了"，而那个只管同心的**。
所以两面墙都画双线的标准画法，谁都不合。

修法：让 `_diag_dedupe` 对斜墙和正交墙一视同仁（按角度聚簇本来就能处理 0°/90°），
拆成 `_split_to_segments` / `_angle_groups` / `_merge_dir_group` 三段。

## 三、改的过程中真值测试抓出三个吞墙缺陷（都是既有的）

在 `tools/plan_eval.py` 加了 `eval_wall_merge()` —— 7 个几何真值用例，
不需要 DXF/Revit，直接喂 plan 给 `consolidate_walls` 判"该并的并了没、不该删的删了没"。
第一版跑出来 3 个坏：

### 缺陷 1：同轴远隔的两面墙被整条删掉
`off < _DIAG_DUP_GAP` 这条"重复线"判据**只看垂距，不看轴向重叠**。
同一条轴线上的两段墙（相隔 5000mm）垂距=0，于是短的那条被当重复线丢弃，
而 `_rechain` 只补 ≤2600mm 的缝，补不回来。实测 8000mm → 4000mm。

修法：加沿向覆盖率 `cov`，要求 `cov > _DIAG_DUP_COVER(0.5)` 才判重复线。
（写这个 `cov` 时我还把下界钳位写成 `min(...,1.0)` 而非 `max(...,0.0)`，
投影落在对侧外反而算出 cov=1.0 —— 被「门洞断墙」用例拦住了。）

### 缺陷 2：门洞断开的墙少一段
同一个根因，间隙 1000mm 的两段（门洞两侧）短者被丢，总长 5000 → 3000。
修后 `_rechain` 正常重连成 0..6000 整墙，洞口交给 Revit 寄宿门窗时切开。

### 缺陷 3：`_resolve_wall_overlaps` 不看楼层，多层图塌成一层
那段同心去重对**全部** items 两两比较，没有分区键。
两层平面上下叠在同一坐标时，二层墙和一层墙 2D 完全同心 → 删掉一层。
合成用例「跨楼层不得串元数据」：给两层各一对双线墙，改前塌成 1 面，改后 2 面。

顺带：`_diag_dedupe` 旧实现让整簇共用 `grp[0]` 的 `level/height/type_hint`。
斜墙时代影响面小，一旦纳入正交墙，全图横墙会被压成同一楼层——
所以新实现先按 `(level, height, type_hint)` 分区，再在区内聚簇。

**厚度刻意不进分区键**：实测有 14~39% 的重复对是"一边标了 240、一边没标"，
按厚度分组会把它们拆到两个区，反而合不上。这条是量出来才敢这么定的。

## 四、结果

| 指标 | 改前 | 改后 |
|---|---|---|
| 聚类后残余真重复（5 图合计段数） | 1111 段 | 345 段（**−69%**） |
| 墙线总长保留率 | 32~52% | **46~71%，合计 56.0%** |
| 带实测厚度的墙占比 | 28~50% | **76~86%** |

保留率这一行是重点：改前 r2 只剩 35%、r4 只剩 32%，**远低于双线取中的理论值 50%**，
说明那时被删掉的不只是重复线，而是真墙。修完三处缺陷后 r2 墙线从 2963m 回到 6069m（**+105%**）。
也就是说这次改动找回的墙比它合并掉的重复更多。

`tools/probe_double_line.py` 保留为通用工具（吃路径或 `@清单`），
它的"保留率"一栏就是防吞墙的哨兵——低于 50% 就该怀疑。

## 五、还没解决的

- 弧类实体（ARC/CIRCLE 不进 entities）仍未修，真图 r3 弧类占 7.2%。

## 六、真机验收（2026-10-08，仙湖别墅.rvt）

重启 Revit 跑 DWG 翻模后按桥量：**361 堵墙里 307 堵是这次翻模建的**
（另 54 堵是模型原有的复合墙）。

| | 原始 CAD | 真机结果 |
|---|---|---|
| 真重复率 | 65~82% | **4.2%**（13/307） |
| 拿到正确 240 厚 | — | 281/307 = **92%** |
| 零长墙 | — | **0**（最短 399mm） |

用户目视确认「基本上没有出现错位问题」。

### 但量出两个新问题

**1. 墙类型污染：10 种，其中 26 堵是不存在的墙厚**

```
DWG-240厚 281   DWG-400厚  8   DWG-309厚 8   DWG-387厚 3
DWG-436厚   2   DWG-433厚  1   DWG-411厚 1   DWG-310厚 1
DWG-248厚   1   DWG-300厚  1
```

每出现一个新厚度值就往项目里克隆一个 WallType。查下来根因是
`_DIAG_MERGE_GAP = 450` 太松：8 堵 `DWG-400厚` 全是 10~16m 的长竖墙，
那是**两面独立墙被当成双线并成一面**。

**2. 桥读不出墙在哪一层，而且我的第一版修复静默失效**

`do_get_elements` / `do_query_elements` 解析宿主楼层只试
`FAMILY_LEVEL_PARAM` / `FAMILY_BASE_LEVEL_PARAM`，墙没有这两个参数 →
所有墙 `level=""`，`level` 过滤器对 8 个楼层全部返回 0。
另外 `do_get_element` 读 `cmd["id"]` 而 schema 声明的是 `element_id`，
按文档调用会返回不相干构件（实测返回 id=1「工程阶段信息」）且不报错。

**我第一版修这个的时候又犯了一次同类错**：候选表里写了
`WALL_LEVEL_PARAM / FLOOR_LEVEL_PARAM / CEILING_LEVEL_WITH_PARAM /
STAIR_BASE_LEVEL_PARAM`，并且用 `hasattr` 过滤"不存在的成员"——
**这四个名字在 Revit 2019 的 `BuiltInParameter` 里根本不存在**，
于是候选表被过滤成**空**，helper 对每个构件都直接返回 `""`。
表面上"部署了、没报错"，实际上什么都没做。是 `get_element` 那次修复
**生效了**而 level 依然全空，这个反差才把问题暴露出来。

真机 `dir(BuiltInParameter)` 实测：墙上能取到楼层的是 **`WALL_BASE_CONSTRAINT`**
（→ 311 → "标高 1"）；`LEVEL_PARAM`、`SCHEDULE_LEVEL_PARAM`、
`ROOF_BASE_LEVEL_PARAM`、`RBS_START_LEVEL_PARAM`、`FAMILY_BASE_LEVEL_PARAM` 存在；
我原先写的四个全不存在。

修法三件事：候选名单换成实测存在的名字；命名参数全落空时**扫一遍参数找值
指向 Level 的那个**（跨类别跨版本都有效）；候选表为空时**直接 raise**——
"守卫本身失效"正是这一整轮在治的病，宁可桥起不来也不能静默返回空。

### 3. 把 `_DIAG_MERGE_GAP` 用真图分布定成 330

不再拍数：量了 5 张真图上"最近平行对"的垂距分布（只统计轴向重叠 >60% 的对）：

```
100-120mm 1654 | 120-140 696 | 180-200 3715 | 200-220 9268(主峰)
220-240 293 | 240-260 3075 | [谷] 260-280 仅 11 | 280-300 55
300-320 518  ← 夹在两个谷之间的独立峰 = 300mm 剪力墙
[谷] 320-340 仅 19 | 340-400 ~372 | 400-420 207 | 440-720 每档 88~192
```

先收到 300，发现 r1 残余重复从 33% 涨到 40.5%——300-320 那个 518 的独立峰
是 **300mm 剪力墙**（真图常见厚度），被我误伤。界线应该落在 **320-340 那个谷**上。
改成 330 后：r4 2.5%（比 300 时的 4.0% 更好）、r1 35.5%、r2 4.5%、r6 32.5%，
墙线保留率合计 56.7%，仍贴着 50% 的理论值。

新增真值用例「400mm间距不得当双线并」把这条界钉住，防止以后又被调回去。

### 待办

- r1/r6 残余 32~36%：这两张 48~56% 图元在 0 层，墙层里混着不该建的东西，
  80~420mm 窗口内配不上对。要继续降得逐图看，不是调参能解决的。
- `suppress_join=True`：合并成中线单墙后角部本可让 Revit 自己接，值得单独试一次真机。

## 七、第二次真机验收（2026-10-08，楼层修复生效后）

楼层读取修好了：**361 堵墙全部在标高 1**。这有两个含义——

1. 上次那个 4.2% 残余重复里**不含跨层误报**，它是真的重复。
2. 翻模把 307 堵墙 + 1733 根柱 + 19 块板全压在同一个楼层上。单张平面图这是对的，
   但多张平面叠在同一张 DWG 里就会全部堆到标高 1。

### 顺带纠正我自己一个猜测

看到 921 条轴网，我猜是"虚线线型被拆成一段一段，每段建成一条轴网"。
量下来**错了**：轴网长度中位数 3874mm、p75 6000mm，只有 76 条短于 1m。
真实原因是中国施工图**按开间逐段画轴线**（每跨一条，端点接气泡编号），
不是虚线段。这条记下来是为了提醒：机制要量出来，看着像什么不算。

（不过确实有 8 条 248.5mm 的轴网和 27 条 <300mm 的，那些是垃圾，值得单独收口。）

### 柱类型：1733 根柱被静默统一成一根型钢

`get_elements` 的类型分布里跳出来：**1733 根柱全是 `UC305x305x97`**，
而位置有 1729 个不同坐标——不是重复建造，是**类型选择器只挑了一个**。

查实现踩到两个坑：

**坑 A：我一开始改的是死代码。** 我先重写了 `bimconv_elements._column_symbol`，
写完一 grep 发现它**只被 `bimconvert.py` import、从没被调用过**。
真跑的是 `bimconv_build.py` 里的闭包 `get_sym`。

**坑 B：真正的问题在 `get_sym` 的兜底。** 它写着

```python
base = col_syms if col_syms else all_syms   # 没有柱族 -> 任意族类型首枚
sym_cache[hint] = _pick(base, hint)          # _pick 无 hint 时返回 pool[0]
```

`all_syms` 兜底会把一扇门当柱建；`pool[0]` 取决于收集器顺序、不可复现。
**同一个洞 v2.9 已经在门窗侧堵过**（注释原话："不再用 all_syms 兜底——回退会把
门建成窗/立柱，缺族就明确失败"），柱这一条当时漏了。

修法：抽出唯一实现 `pick_column_symbol(pool, hint)`，`get_sym` 调它，
空池返回 `None`（走已有的"项目中没有可用的柱族类型，已跳过"明确失败路径）；
`hint` 命中优先，否则偏好混凝土柱（施工图柱绝大多数是混凝土），
再退到按名字排序的首枚以保证可复现。

### 那句"靠预览提示"是个不存在的安全网

原 docstring 写着兜底"仍可能不对，**靠预览提示**"。查 `DWG翻模/script.py`：
预览里关于柱只有一行安全模式说明，**从没显示过柱类型**。
所以 1733 根柱的类型是彻底静默决定的。现在预览会显示

> 🏗 柱将**统一**使用族类型 **X**（规则未指定类型，施工图柱多为混凝土；
> 需要别的类型请在 mapping_rules.csv 的 type_hint 列填写后重跑）

### 测试：一次是我断言写错，一次是代码契约没写明

`pick_column_symbol` 加了 4 组断言。过程中：

- 我第一版断言"应选中混凝土-矩形 400x400"——**错的是断言**：按名排序后
  圆形（圆 U+5706）排在矩形（矩 U+77E9）前。要紧的性质是"落在混凝土集合内
  且可复现"，不是"哪一根"。改成断言性质。
- 第二版断言"池里有门时不能选门"——**这条暴露了真问题**：函数不看类别，
  类别过滤是 `_column_pool` 的职责。活路径传的是已筛过的 `col_syms` 所以安全，
  但契约没写。于是在 docstring 里写明"pool 必须已按类别筛过"，断言改为只传柱族。

反向验证：把 `pick_column_symbol` 退回旧的 `syms[0]`，断言立刻红，
报的正是真机那个症状 `应只在混凝土柱里挑，实得 UC305x305x97`。

## 八、第三次真机验收：门窗从来没被建出来过（2026-10-08）

换了一张更大的图重跑，量到：墙 2048、柱 3973、板 46、轴网 1691、**门 0、窗 0、楼梯 0**，
全部落在标高 1。2048 条墙定位线**端点零重复**（不是叠加，是新图）。

柱仍是同一个类型（3973 根全 `457 x 475mm`）。追下去之后，找到了整条链路上
**最严重的一个 bug**：

### 三个族类型池恒为空

| 族 | 对 `OfClass(FamilySymbol)` 结果按 `s.Category.Name` 筛 | 收集器级 `OfCategory(...)` |
|---|---|---|
| 门 | **0 个** | **12 个** |
| 窗 | **0 个** | **31 个** |
| 柱 | **0 个** | **3 个** |

`bimconv_build` 里 `col_syms` / `door_syms` / `window_syms` 全是
`s.Category and u"门" in s.Category.Name` 这种写法。在 Revit 2019 + IronPython 2.7
下，从 `OfClass(FamilySymbol)` 拿到的符号，其 `.Category.Name` **取不到门/窗/柱**
（实测那 266 个符号的类别名全是"专用设备标记""体量楼层标记""停车场"这类注释类别），
而同一批符号用 `OfCategory(BuiltInCategory.OST_Doors)` 能正常拿到、且
`.Category.Name` 就是"门"。

**后果**：
- 门窗**一次都没被建出来过**，而报的错是"项目中没有可用的门窗族（FamilySymbol），
  已跳过；请载入门/窗族后重试"——**把筛法 bug 报成了缺资源**。项目里明明有
  12 个门族、31 个窗族。这是"效果不好"里最实在的一条：门窗全缺。
- 柱能建出来，纯粹是因为当时 `get_sym` 有 `col_syms if col_syms else all_syms`
  这句错误兜底，从全项目族里抓了第一个。**我上一轮把兜底删掉、却没修筛法，
  会让柱也全部失败**——这是我引入的回归，这次一并修掉。

### 修法

三个池一律改成收集器级 `OfCategory(BuiltInCategory.OST_xxx)`；
`_column_pool` 同时保留按名筛作补充（有些项目柱族不在这两个类别下）。
删掉已无引用的 `all_syms`（它还是一次无用的全项目扫描）。

### 过程中撤回的两个我自己的错判

1. **"type_hint 从来没生效"——撤回。** 我看到 `bimconv_elements` 里
   `def type_name(et): try: return et.Name except: return u""`，又实测
   `FamilySymbol.Name` 确实抛 `AttributeError`，就下结论说所有类型匹配都在拿空串比。
   **错**：那个定义只在 `from bimlib import type_name` 失败时才用，
   而 `bimlib.type_name` 早就知道这个坑并回退到 `ALL_MODEL_TYPE_NAME`（注释里
   写着"真机验证可用"）。实测 `SYMBOL_NAME_PARAM` / `ALL_MODEL_TYPE_NAME` 都能
   取到 `457 x 475mm` 等真名。
2. **第一次量 `colpool_n: 0` 不可信。** 那段探针代码里我直接写了中文字面量
   `u"柱"`，经 JSON 传给桥时可能被改坏。改成纯 ASCII 源码 + `\u67f1` 转义重测，
   结论仍然成立（0 vs 3），这才敢当证据。

（顺带又记一条：`BuiltInParameter.ELEMENT_NAME` 在 2019 不存在——我这轮第二次
凭印象编枚举名了。同一个教训：`dir(BuiltInParameter)` 实测，别照文档写。）
