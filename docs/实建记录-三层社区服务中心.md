## 三、撞出的两个真实缺陷

### 缺陷 1：`model_builder.py` 导入即失败 —— 两个按钮一点就炸

`lib/model_builder.py:37` 原本是：

```python
from System.Runtime.CompilerServices import StrongBox
```

在 Revit 2019 + pyRevit IronPython 2.7.12 上**直接 ImportError**：

```
Cannot import name StrongBox
```

**受影响**：「AI 智建」面板下的 **「一键建模」** 与 **「一键演示」**
（两者都 `from model_builder import build_model`）。

**同仓库的 `bridge_core.py:1774` 用的是正确写法** `from clr import StrongBox` ——
那条路是通的（桥一直能用）。以它为准修掉，并保留旧写法兜底。

**修完在真 Revit 里验过**，无头建模全程跑通：

```
### 1/7 创建标高...  标高: 4 个
### 2/7 创建外墙...  外墙: 12 堵
### 3/7 创建内墙...  内墙: 15 堵
### 4/7 创建楼板...  楼板: 4 块
### 5/7 创建坡屋顶... 屋顶: 已创建
### 6/7 创建门窗...  窗户: 42 | 门: 1
### 7/7 创建阳台...  阳台: 2 个
统计: {"fail_count": 0, ...}
```

**为什么 8 关测试没抓到**：harness 用的是宽松打桩，任何 import 都会被自动补上 ——
于是又是**一次假绿灯**。这类"真机命名空间"问题，**只有真跑才看得见**。
（S7 消灭了三处"永远通过"，这是第四处，性质不同：前三是逻辑不覆盖，这个是环境不可模拟。）

### 缺陷 2：`gable_roof` 把屋面建成了**楼板**

验收报 `OST_Roofs: 0`、`OST_Floors: 6`。逐元素查证后：

```
id=333915  category=楼板  class=Floor  name=常规 - 150mm  厚度=150mm
```

屋面步骤的日志是：

```
[gen:屋面1] {"variants": [8 个全部 "Invalid profile."], "made": {"id": 333915 ...}}
```

**8 个挤出方案全部失败后，回退把屋面建成了楼板** —— 3D 里看着像屋面
（导出图上确实是双坡），但语义上它不是 Roof：不进屋面明细表、不被屋面过滤器找到、
剖面/立面里也不按屋面标注。

而 `OST_Floors: 6` 的构成也就清楚了：

| 数量 | 是什么 |
|---|---|
| 3 | 真正的楼板（333597 / 333605 / 333613） |
| 2 | **楼梯平台**（333750 / 333851）—— Revit 里平台本来就归楼板类别 |
| 1 | **那个被当成屋面建的楼板**（333915） |

**所以 `expect.floors` 这种"按类别计数"的验收判据本身也偏粗**：
楼梯平台合法地落在楼板类别里，光看计数分不清"多出来的是平台还是错件"。
这次是逐元素查类别才定位到的。

> 缺陷 2 **尚未修**。它涉及 `gable_roof` 的挤出回退逻辑，
> 属于几何算法改动，不适合在这轮顺手改 —— 记录下来单独处理。

## 五、结论

这一轮值得记的不是"建出了一栋楼"，而是：

> **真跑一遍，比八关测试更能说明问题。**

S7 把测试覆盖从 7 个按钮扩到 19 个、加了 `--strict`、消灭了三处假绿灯；
但这两个缺陷它一个都没抓到 —— 一个卡在**环境模拟不了**（真机命名空间），
一个卡在**没人真去看建出来的东西对不对**（屋面类别）。

**测试能证明"没崩"，证明不了"建对了"。**
