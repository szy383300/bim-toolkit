## 一、动手前的侦察（推翻了一个假设）

原以为障碍只有"没装 `git-filter-repo`"。实测后发现**一个更该先修的隐患**：

```
_train/      1819.7 MB    ┐
_models/     1241.8 MB    │  这 5 个目录
_research/    147.0 MB    │  **都没有被 .gitignore 忽略**
_snapshots/    27.8 MB    │
models/       384.0 MB    ┘  （models/ 里是 55 个 .rvt）
```

合计约 **3.6 GB 的生成数据**悬在工作区里处于"未跟踪"状态 ——
**一次 `git add .` 就会把它们全部提交进去**。这比密钥问题更容易伤人。

而重写历史又要求工作区干净，所以顺序只能是：**先修忽略规则 → 再重写**。

### 补齐的忽略规则

沿用本仓库既有的"下划线前缀 = 本地工作区"约定（`_tools/` `_train/` `_research/` …），
新增忽略：`_train/` `_models/` `models/` `_research/` `_snapshots/` `analysis/`
`buildings/logs/` `_survey/` `mcp/_*` `mcp/.workbuddy/`。

### 顺带确立的流程

重写前必须工作区干净 → 所以把本轮的改动作一次提交。

**提交前加了一道安全闸**（这一步救了我一次误判）：

```bash
git diff --cached | Select-String '^\+' | Select-String 'sk-[0-9a-f]{16,}'
```

> 第一次跑的是不带 `^\+` 的全量 diff，报了"⚠️ 发现密钥" ——
> 差点以为要误提交。核实后是**删除 diff 里被移除的那一行**：
> `deepseek_config.json` 正被 `git rm` 掉，那 7 行都是 `-`。
> **只看新增行**才是对的判据。

| 1 | 补 `.gitignore`（3.6 GB 生成数据） | 工作区条目 91 → **53** |

| 4 | 装 `git-filter-repo` | 2.47.0 |
| 5 | 外科式替换 | `--replace-text`：`sk-637d…==>***REMOVED-REVOKED-KEY***` |
| 6 | 清 `filter-repo` 中间目录 | 里面存着替换表 |

**为什么用 `--replace-text` 而不是 `--path … --invert-paths`（删掉整个文件）**：
替换能**保留那个文件与它的完整历史**，只把密钥换成占位符 —— 更外科、更少副作用。
删文件会让历史里凭空少一个配置文件的演进过程。

## 五、关于那个 335 MB 的备份（需要你决定）

`E:\bim-toolkit.git-backup-20261001-190559` 是**重写前的完整 `.git`**，
也就是它**仍然包含那个已作废的 Key**。

**我的判断：先留着。**

- 它在**仓库外**，不会随 clone / push 传播 —— S2 的目标（不让密钥跟着仓库走）**已经达成**
- 里面那个 Key **已在 S1 吊销**（HTTP 401 实测），对攻击者零价值
- 而它是这次不可逆操作的**唯一回滚点**

确认一切正常后想彻底清掉，执行：

```powershell
Remove-Item -LiteralPath 'E:\bim-toolkit.git-backup-20261001-190559' -Recurse -Force
```

> 删了就**没有回滚点**了（filter-repo 已把旧对象 gc 掉，仓库内已无旧历史）。
