# S19 · 翻模改吃"一套图"：Stage 1（分层归位 + 墙高跟层高）

日期：2026-10-08 ｜ 影响：`DWG翻模/script.py`、`lib/bimconv_rules.py`、`lib/bimconv_build.py`、`mapping_rules.csv`

## 起因：用户的判断是对的

真机翻模能出墙、开门窗洞之后，用户提出：

> 我在想是不是我的图纸不够专业以及只靠一张平面图当前的运行逻辑无法确认该怎么建墙、门窗、楼梯等所有构件

核实后：**不是图纸问题，是单张平面图在几何上欠定。** 真实施工图 98% 图元在具名图层、
门窗表齐全，画法规范。缺的是信息本身：

| 要建的 | 平面图里有没有 | 改之前从哪来 |
|---|---|---|
| 墙厚 | ✅ 双线间距 | 实测（S18 已修好） |
| **墙高** | ❌ 完全没有 | CSV 写死 3000 |
| **这面墙在几层** | ❌ 二层平面和一层平面长得一样 | 全部落到 `levels[0]`（实测 2048 堵墙都在标高 1） |
| **窗台高 / 洞口高** | ❌ 只有洞口宽度 | 规则写死 1500/2100 |
| **楼梯踏步数 / 行进方向** | ❌ 平面只画踏面 | 退化成 DirectShape 盒子 |

所以三维视图里那些深窗洞盒子、墙高不齐，不是识别错，是**在替缺失的信息猜**。

## 分阶段路线

- **Stage 1（本篇）**：多文件 + 每张图按文件名归层 + 墙高从模型层高算。不需要新解析。
- **Stage 2**：门窗表入库（`lib/door_schedule.py` 已能解析出
  `{code, width_mm, height_mm, type_name, counts:{“1层”:24}}`，但是**孤儿模块，全仓没人 import**），
  用真实洞口高/窗台高替掉写死值。
- **Stage 3**：平面上的门窗编号文字（TEXT）与门窗表行匹配，按编号分派族类型。

## Stage 1 做了什么

### 1. 文件名 → 楼层（`level_from_filename`）

原有 `_infer_level` 只做 token 匹配，要求 token **同时**出现在图层名和楼层名里。
但项目楼层普遍叫「标高 3」，文件名普遍叫「三层平面图.dwg」——
"三层" 不在 "标高 3" 里，永远配不上，于是整套图全落到 `levels[0]`。

新增一条按**层号**对齐的路径：中文数字/`N层`/`NF`/`负X层`/`地下X层` → 层号 →
再与项目楼层名的层号（`_level_number_of`）对齐。

优先级：**规则指定 > 文件名 > 图层名 > 兜底首个楼层**。
文件名是整张图的证据，比图层名强。

### 2. 墙高跟随层高

CSV 里 `height` 留空/0 的语义从"用 10ft 缺省"改成**「跟随本层层高」**：
`bimconv_build` 从项目的 `Level.Elevation` 排序后算出每层到上一层的高差表，
墙 plan 的 height 为 0 时按它填。墙类规则的 3000 全部改成 0；
阳台栏板保留 1100（那是特意矮的，不是猜的）。

### 3. 多文件

`OpenFileDialog.Multiselect = True`，`_pick_drawing()` 返回列表。
逐张转换 + 逐张出计划（各自带 `file_hint`），合并后**统一归并一次**——
`consolidate_walls` 按 `(楼层,层高,类型)` 分组，不同层的墙不会被误并。

### 4. 预览摊开"每层是怎么定的"

```
图纸                落到楼层      定层依据
三层平面图.dwg      标高 3        按图纸文件名×412
标准层.dwg          标高 1        兜底取首个楼层×388
```

并且**兜底数量单独告警**：归错层不报错，只会把整层墙叠到别层上，比不建更难查。

上面第一条"另一个量级"这一周真的撞上了。用户跑的是
`房屋设计图\小区住宅楼建筑结构施工图 270套`，不是我一直在测的六号教学楼语料，
所以我第一次离线复现"成功"却解释不了现场——**语料不对，复现就没用**。

### 一、没有崩：报表口径把成功说成了失败

最新两份日志（2026-10-11 10:15 / 10:29，部署之后）：

```
多层户型平面   planned=1517   ok=1080  fail=437   delta=1293  ✅ 对账通过
高层平立面图   planned=10951  ok=9823  fail=1128  delta=12545 ✅ 对账通过
```

失败原因去掉数字后统计，两份日志各自 98% 以上是同一句：

```
高层：安全模式已跳过 window ×646、door ×460   真失败：楼板 22 + 墙重叠 Warning 10
多层：安全模式已跳过 window ×242、door ×195   真失败：墙重叠 Warning 10
```

`安全模式` 是模式弹窗里【是】那一档（文案写着"真图首选"），按设计就不建门窗楼梯。
它却被计入 `fail` 并逐行排成红色「失败原因」表——上千行红字把
「9823 个已落盘、对账通过」整个盖掉。**读数的人没有任何办法把它当成成功。**

修法：抛出侧与统计侧共用一个 `SAFE_SKIP_TAG` 常量（两边各抄一遍中文必然漂），
结果分「成功 / 按所选模式跳过 / 失败」三档，日志只逐行写真失败。

### 二、真问题：一张 DWG 里有 23 张子图，全部叠在同一个楼层

`subdrawing_clusters()` 只按坐标做 10 m 网格八邻接连通（不看图层名——立面图上
画的墙线用的就是和平面一样的 `WALL` 层名，只有"画在图纸哪一块"能区分它们）。
用**部署后的 lib** 按按钮同款链路重放：

| 图纸 | 计划构件 | 子图簇 | 簇内占比 | 实际用到的楼层 |
|---|---|---|---|---|
| 高层/平立面图 | 10951 | **23** | 10771/10951 = 98.4% | **1** |
| 高层/地下室 | 3746 | 10 | 3653/3746 = 97.5% | 1 |
| 多层户型平面 | 1517 | 7 | 1509/1517 = 99.5% | 1 |

计划构件数与真机日志**逐个数字一致**（10951 / 1517），说明这条离线链路就是
按钮那条，也说明这 23 张图在真机上确实全建在了一层。
墙重叠 Warning 由此而来，不是合并算法错。

**Stage 1 的「按文件名定层」对这套图结构性无效**：文件名是
`平立面图.dwg` / `地下室施工图.dwg`，层号不在文件名里，在**图面分块里**。
这一套图的组织方式是"一张文件画完所有层 + 立面 + 剖面"，
而路由单位一直是"文件"。

顺带一条：这三张住宅图的 `texts` 有 1101 / 402 / 58 条，
但门窗编号**一条都没有**（`coded=0`，1106 个洞口全靠规则默认尺寸）。
命中的四位数字是"七层建筑面积1062.2M"这类标注。教学楼 r4 是 `coded=650/decoded=521`，
所以 Stage 3 的解码逻辑本身没问题，是这套语料不按分米编号写在平面上。
